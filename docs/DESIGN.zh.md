# 设计与管道

English version: [DESIGN.md](DESIGN.md)


## 1. 我们在做什么

在网络连接较弱的地方，小型餐饮和住宿商户常常没有出现在在线地图和预订网站上。这些商户的店主可能只有一部功能机。去那里的游客无从得知在哪里吃饭、在哪里住宿。

- **商户**（本地商户）用任何手机发短信，以自己的语言报告自己提供什么。服务器把每条短信转成结构化的商户条目（地点、提供的内容、价格、营业时间、联系方式），并保留原文和一份英文译文。
- **游客**在有网络连接时下载某个村或某个区的商户条目，之后在手机上搜索，完全不需要网络连接。他们也可以用自己的话提问：有数据网络时由服务器根据商户条目回答；只有手机信号时，同样的问答可以用短信进行；完全没有网络时，由手机上的小模型把问题转成搜索。

## 2. 设计原则

1. **管道与地区无关。** 所有与具体地点有关的内容（语言、货币、关键词、村名表、回复文本、电话号码格式）都放在地区配置文件（`regions/<id>.json`）里。增加一个地区，就是写一个新的配置文件，而不是改代码。印尼的 Samosir 只是第一个测试配置文件。
2. **只在固定规则做不了的地方用 AI：** 把自由文本短信转成各个字段，以及翻译。关键词、价格、营业时间、电话号码和村名先用规则解析。
3. **游客端不用任何 AI 也能工作；AI 是额外的帮助。** 在小型地区数据包上做离线搜索，能在任何手机上立即回答大多数问题，而且几乎不耗电。游客用自己的话提的问题，由服务器根据商户条目回答；完全没有网络时，由手机上一个可选的小模型回答，它只负责把问题转成搜索筛选条件。
4. **缺什么就问，不要猜。** 如果缺少必填字段，服务器会像做问卷一样，给店主发一条简短的短信提问，而不是让模型去填。
5. **每条条目都由其店主确认。** 服务器用短信回复一份摘要；店主回复 `1` 表示确认。每条条目都显示最近一次确认的时间。一个电话号码只能编辑它自己的条目。
6. **发布前先取得同意。** 只有店主同意，店主的电话号码才会显示给游客。
7. **任何模型都可以接入。** 服务器通过一个模型接口访问语言模型；默认是我们自己 GPU 服务器上的一个小型开源模型，修改设置即可换成托管 API。
8. **宣称的内容要么已测量，要么有标注。** 文档中的每个数字，要么由本仓库里的脚本测量得出，要么标明是估计。

## 3. 地区配置文件

地区配置文件（示例：[`regions/samosir.json`](../regions/samosir.json)）定义以下内容：

| 字段 | 示例（Samosir 测试配置文件） |
|---|---|
| OpenStreetMap 查询的区域 | `Samosir`，行政级别 5（县） |
| 商户语言 | 印尼语（`id`）；巴塔克托巴语（`bbc`）作为拓展目标 |
| 游客语言 | 英语 |
| 货币和简写 | IDR；`25rb` = 25,000；`1,5jt` = 1,500,000 |
| 短信关键词 | `MAKAN`（餐饮）、`INAP`（住宿）、`TUTUP`（不营业）、`BUKA`（营业）、`CARI`（搜索） |
| 村名表 | 来自 OpenStreetMap 的 place 点位，之后改用官方村名表 |
| 回复模板 | 印尼语的确认和追问 |
| 电话格式、时区 | `+62`、`Asia/Jakarta` |

## 4. 管道

### 4.1 商户端：短信 → 商户条目

```
商户的手机（短信）                                 [此版本不含语音]
   │
   ▼
装有 SIM 卡并运行短信网关应用的 Android 手机 ──► POST /webhooks/sms
   │
   ▼
1. 识别发送者       电话号码 → 商户记录（收到第一条短信时创建）
2. 判断意图         来自地区配置文件的关键词规则（MAKAN / INAP / TUTUP / 1 / CARI ……）
3. 解析字段         规则优先：价格、营业时间、电话、村名（与村名表模糊匹配）
4. 提取其余字段     模型把自由文本中的其余字段填入商户条目 schema，
                    经由模型接口（§4.5）进行；未配置模型时，只用规则
5. 校验             JSON Schema + 核对（价格范围、村庄存在、营业时间有效）
6. 缺失则追问       每个缺失的必填字段发一条短信提问（名称、村庄、提供的内容、价格）
7. 翻译             保留原文；添加英文（语言模型，或翻译模型）
8. 确认             回发短信：摘要 + "Balas 1 jika benar"（正确请回复 1）
9. 存储             SQLite：商户条目 + 原始短信 + 英文 + 提取方式；
                    语音音频从不存储
```

必填字段：类别、名称、村庄、提供的内容、价格（或 "ask"）、营业时间（或 "ask"）。可选字段：容量、地标、不含照片的描述、同意公开电话号码。

### 4.2 游客端：四种获得答案的方式

| 网络连接 | 游客如何提问 | 由什么回答 |
|---|---|---|
| 数据网络（在热点处） | 应用下载地区数据包 | 服务器导出：每个村或区一份 JSON |
| 无 | 在应用里搜索 | 在数据包上做本地筛选：类别、村庄、价格、现在营业、距离（GPS 离线也能用）。不用 AI。 |
| 只有手机信号 | 发短信 `CARI makan Garoga` 或自由文本 | 服务器匹配商户条目，用最多 2 条短信（每条 160 个字符，只用普通字符）回复前 3 条 |
| 数据网络 | 在应用里用自己的话提问 | 规则先挑出候选商户条目；服务器上的语言模型只根据这些条目回答，并引用条目 ID；回答要通过核对，否则由规则组合答案（`server/offgrid/chat.py`） |

没有网络时：一个可选的小型设备端模型（Qwen2.5-0.5B-Instruct，在浏览器里运行），只负责把自由文本问题转成搜索筛选条件。回答文本由商户条目行生成，所以模型无法编造地点。

以搜索词（`SEARCH`、`CARI`、`搜索`）开头的搜索仍然完全靠规则。用自己的话提的问题，不论在应用里还是用短信，都由服务器上的模型根据商户条目回答（本演示中为模拟输出），规则作为后备。

### 4.3 数据

- **商户条目记录：** [`schemas/listing.schema.json`](../schemas/listing.schema.json)。
- **地区数据包：** `{region, generated_at, villages[], listings[]}`，只含已确认的条目，只有取得同意才包含电话号码。预期大小：每个村 KB 量级。
- **短信日志：** 每一条收到和发出的短信及其时间戳，用于调试和评估。

### 4.4 哪里用到 AI

| 步骤 | 方法 | 用 AI？ | 没有语言模型密钥时 |
|---|---|---|---|
| 意图、价格、营业时间、电话 | 来自地区配置文件的规则 | 否 | 相同 |
| 村名 | 与村名表模糊匹配 | 否 | 相同 |
| 自由文本字段 | 带商户条目 schema 的语言模型 | 是 | 通过短信向店主追问缺失的字段 |
| 翻译成英文 | 语言模型或翻译模型 | 是 | 只显示原文 |
| 游客的短信提问 | 关键词解析，自由文本用语言模型 | 部分 | 只支持关键词格式 |
| 游客提问（应用和短信） | 语言模型只看候选商户条目，然后核对 | 是 | 由规则根据商户条目组合答案 |
| 离线搜索 | 在数据包上筛选 | 否 | 相同 |

### 4.5 模型接口

所有模型调用都经过一个函数：`complete_json(task, text, schema) -> dict`。它后面对接：

| 提供方设置 | 连接到 | 用途 |
|---|---|---|
| `openai_compatible` | 任何支持 OpenAI API 格式的服务器：Ollama、vLLM、llama.cpp；大多数托管 API | 之后的部署，例如 Qwen3-1.7B |
| `anthropic` | Anthropic API | 可选的托管替代方案 |
| `simulated` | 一个示例短信文件，附带预先写好的输出 | **演示**：服务器上不运行任何模型 |
| `none` | 无 | 规则加短信追问 |

设置放在 `.env` 中（`LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY`）。提示词是 `models/prompts/` 里的文件，每个任务一个（提取商户条目、翻译、解析游客问题、根据商户条目行作答），这样不用改代码就能修改提示词并重新评分。

## 5. 评估

| 评估项 | 方法 | 输出 |
|---|---|---|
| 提取准确率 | 不报告：没有模型运行，而给我们自己写的输出打分，什么也测量不出来 | — |
| 游客短信搜索 | 15 个问题，附有预期的商户条目 | 正确条目出现在前 3 条中的百分比 |
| 数据包大小和离线搜索 | 真实手机，飞行模式 | 每个村的 KB 数；搜索耗时；能否工作（是/否） |
| 成本 | 每条商户条目的短信条数；每条短信的语言模型 token 数 | 每条商户条目的成本 |

所有示例短信都是 Claude 编造的，并标注为合成数据。自动化测试（`server/tests`）用这些短信核对管道能否端到端工作；它们不能证明在真实短信上的准确率。不运行也不比较任何模型。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 网关手机没电、没信号，或应用停止运行 | 保持手机有电并连着 Wi-Fi；模拟器页面作为后备 |
| 在只有 CPU 的服务器上模型太慢 | 立即回复网关，模型处理完成后再发出短信；关键词短信跳过模型；改用方案 A |
| 测试短信还没有经过懂印尼语的人核对 | 只给不读印尼语也能核对的字段打分；把测试短信标注为 AI 撰写 |
| 演示服务器宕机 | 用 `deploy/deploy.sh` 重启；之后通道的地址会变 |
| 小模型返回损坏的 JSON 或错误的字段 | 用 JSON schema 约束输出；校验；字段不通过时通过短信询问店主 |
| 笔记本电脑休眠，或通道 URL 变化 | 保持笔记本盖子打开；重启后更新 webhook URL |
| 条目有误或已过期 | 店主确认、最近确认日期、只有店主本人的号码才能编辑 |

## 7. 已经有谁在做这件事

重合度最高的排在前面。标有（未重新核查）的各项来自记忆，今天没有重新核实；我们还没有搜索过这个完全相同的组合，而且没有找到某样东西，并不等于它不存在。

- **世界银行印尼旅游项目：** 为 20,000 多个商户建立了在线档案；没有报告收入方面的结果（世界银行 2025 年十年旅游回顾，出自我们的文献笔记）。
- **政府的旅游村平台**，例如印尼的 Jadesta 旅游村名录（未重新核查）。
- **Google Maps、预订网站和 OpenStreetMap：** 已经收录了游客集中的热门旅游中心；离线地图应用（Organic Maps、OsmAnd）可在没有网络连接时显示 OSM 地点（未重新核查）。
- **把短信众包到数据库或地图的系统：** Ushahidi、FrontlineSMS（未重新核查）。
- **功能机语音平台，让当地人录制报告：** Gram Vaani 的 Mobile Vaani、CGNet Swara（印度）（未重新核查）。
- **已部署的、通过短信接入云端 AI 服务的系统：** 医疗领域的 Jacaranda Health PROMPTS（肯尼亚）、Babyl（卢旺达）（出自我们的案例回顾，2026-10-03）。

我们的不同之处在于细节，而且尚未验证：商户用自己的语言通过短信自行登记；条目经过确认并标注日期；游客拿到可离线使用的地区数据包；同一套管道通过配置文件复用于任何地区。

## 8. 下一步

- 与当地旅游团体或村办公室开展试点，它们可以提供第一批条目（一次性走访或调查）并推广短信号码；之后商户通过短信让条目保持最新。
- 通过当地短信服务商获得本地号码或短代码；决定由谁来支付商户的短信费用。
- 先测量中间结果（创建并保持最新的商户条目数量、游客搜索次数、打给商户的电话次数）。我们的文献笔记没有找到因果证据，能证明在发展中国家把小商户放到网上会提高它们的收入，所以试点应该测量这一点，而不是假定它成立。
