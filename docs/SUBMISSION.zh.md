## 提交文本（草稿）

提交和录音时用英文版原文（docs/SUBMISSION.md），这里的中文只供理解。

**项目名称：** Offgrid Tourism（暂定名称）

**赛题：** 旅游

**一句话：** 本地的餐饮和住宿商户用任何手机、以自己的语言通过短信自行登记；游客离线或通过短信搜索这些商户条目。

**简短描述（约 100 词）：**
旅游中心以外的小型民宿、小吃摊、船只经营者和导游没有出现在地图和预订网站上，而且许多店主只有一部功能机。在我们的测试地区（印尼多巴湖上的 Samosir），OpenStreetMap 上 62% 的餐饮和住宿地点距同一个旅游村 3 km 以内，58% 的村庄附近没有收录任何地点。Offgrid Tourism 让店主用印尼语、巴塔克托巴语或英语发一条短信；固定规则和一个小型语言模型把它变成一条商户条目，店主通过短信确认，游客下载该地区的商户条目（约 28 KB），在没有网络连接时搜索，或通过短信提问。

**工作原理：**
1. 店主用任何手机给服务号码发短信。一部装有本地 SIM 卡、运行开源短信网关应用的 Android 手机，把这条短信转发到我们的服务器。
2. 固定规则判断语言和短信类型，并读取没有歧义的内容：价格、营业时间、房间、来自地区村名表的村名。
3. 小型语言模型处理规则处理不了的内容：商户名称、提供的内容、路线指引和英文译文。模型给出的每个值都必须能追溯到这条短信（名称必须出现在短信中，数字必须一致，村庄必须在村名表里），否则会被丢弃。
4. 缺少的内容通过短信追问，一次只问一个问题。店主回复“1”确认摘要，并决定是否显示自己的号码。
5. 已确认的条目写入一个小文件，每个地区一个。游客端网页应用只下载一次，之后离线搜索；界面可用英语、印尼语或中文。有信号但没有数据网络的游客用短信搜索。

**AI 的使用（以及我们没有做的事）：**
只在固定规则做不了的地方用 AI：读取自由文本短信并翻译。模型通过一个接口访问，所以修改一项设置，就可以接入我们自己服务器上的小型开源模型（我们选了 Qwen3-1.7B）或托管 API。在这次演示中不运行任何模型：我们没有可用的 GPU，而在一台 1 核 CPU 的服务器上测试 Qwen3-1.7B，每条短信大约要一分钟。对于示例短信，模型的输出是预先写好的，并在每个出现的地方都标注为模拟输出；其他任何短信都由规则和追问处理。我们不报告任何准确率数字，因为给我们自己写的输出打分，什么也测量不出来。

**真实世界数据：**
印尼多巴湖的萨摩西县（Samosir），是世界银行印尼旅游发展项目（Indonesia Tourism Development Project）中的一个目的地。我们用一个适用于任何地区的脚本，在 OpenStreetMap 上测量了信息缺口（228 个餐饮和住宿地点；62% 在 Tuk Tuk 3 km 以内；7% 有电话号码；132 个村庄中有 76 个在 2 km 以内一个都没有）。村名和坐标是真实的；演示中的每一个商户、价格和电话号码都是编造的。

**本地化：**
代码里没有任何与 Samosir 有关的内容。每个地区就是一个配置文件：它的语言及其词表、货币和价格简写（25rb = 25,000 印尼盾）、村名表、回复文本和时区。商户用自己的语言书写，包括当地语言巴塔克托巴语；回复回退为印尼语（国家通用语言）。商户端只需要一部功能机和短信；游客端在没有网络连接时也能工作；短信网关使用本地 SIM 卡，按本地资费；模型可以运行在社区自己控制的服务器上。

**局限和后续步骤：**
目前还没有真实用户；巴塔克托巴语的词汇还没有经过母语者核对；Android 网关已构建完成，但还没有连接到手机；没有语音报告。下一步：与 Samosir 的一个旅游村团体开展试点，由它提供第一批条目；请母语者核对；用真实短信评估小模型；测量已登记的商户是否获得更多顾客。

**技术栈：** Python 标准库（HTTP 服务器、SQLite）、可离线使用的网页应用（service worker，离线缓存脚本）、开源的 SMS Gateway for Android、模型接口（OpenAI 兼容 / Anthropic）、JSON Schema、OpenStreetMap（Overpass API）、Cloudflare tunnel。
